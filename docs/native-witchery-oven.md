# WitcheryExtras oven machine contract

Implementation batch status: unverified. The new `witcheryNativeOven` process has not yet been included in a generated contract release or a candidate. The previous `witcheryOven` process remains a historical reader; its final source-version boundary is part of the unified release work.

The pinned inputs are Witchery 0.24.1 and WitcheryExtras 1.3.8. Source inspection of `TileEntityWitchesOvenMixin` and static reading of the existing remapped native-test JAR agree that the tile does **not** call `OvenRecipe.isInputMatch`. The helper's ore alternative and `jars == 0` shortcut must not be used as the machine law. Historical helper tests do not establish tile equivalence.

The actual machine walks the registered list and selects its first non-null literal input for which jar stock is sufficient and `Utils.areStacksEqual` succeeds. NBT presence and value must agree; metadata 32767 on either side is a wildcard. Source input count is ignored. A null literal input cannot be rescued by its ore key in this path. Exclusion of a later definition requires an earlier definition that covers the entire predicate and threshold; enumerated content examples alone are not that proof.

`definitions` retains the ordered literal input, signed jar threshold and registered output gate. The latter is distinct from `furnace`, which contains the actual smelting lookup for the specimen's item. HashMap native walk and the pinned EFR/GTNHLib wildcard-priority maps are read through `NativeSmeltingTable`; neither NEI display caches nor runtime result-cache writes are involved.

An empty main-output slot admits the selected entry. An occupied one must equal the **registered gate** by item and metadata; the wrapped integer sum with the gate's count must fit the inventory and gate item limits. Completion then obtains the **furnace result**. An empty slot copies it; an item/meta-equal existing slot adds its count and retains existing NBT. If the existing slot matches the registered gate but differs from the furnace result, main placement is skipped while input consumption and byproduct attempt still occur. A missing gate in the occupied-slot path, or a missing furnace result on completion, is a native error, not a successful empty result.

The byproduct roll uses the three direction-query contributions in native f64 addition order. The comparison is `roll <= min(1, 0.3 + contributions)`. Normal funnels add 0.25; filtered funnels add 0.3 or 0.8 according to the native configuration. A present jar slot permits the attempt. Exactly one jar is removed only when the side output accepts the byproduct. An empty side slot copies it; an equal existing stack retains NBT and merges only when the wrapped new count is **strictly less than** that existing stack's limit. The tick count is `180 - 20 * attachedFunnels`, with three queried positions. Fuel, world orientation, live inventory limits and interruption remain runtime conditions.

The Java source reader owns its examples and projections, pins native registration/configuration/role/furnace sources, and rechecks at sealing. The Compiler and Catalog validator cross-check concrete input and empty-slot output specimens against the ordered source facts. The page presents these as conditional examples, with separate Chinese and English explanations; the material calculator must not turn them into unconditional fixed production.

The final concentrated check must cover source-instance drift, helper-vs-tile matching, null/empty NBT, wildcard priority, signed arithmetic, different registered/furnace outputs, no-placement input debit, side-slot strict capacity, and separate languages using existing lightweight test tools. These checks have not been executed for this batch.
