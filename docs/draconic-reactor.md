# Draconic reactor reference

The exact `com.brandon3055.draconicevolution.integration.nei.ReactorNEIHandler` page shows three alternative fuels and a chaos shard. Those slots are an illustration of the reactor process, not a one-item-to-one-shard recipe. The dedicated adapter reads native registrations, current ConfigHandler fields and the actually initialized ContainerReactor unit constants without loading or drawing that GUI.

One typed read-only reference contains the core inventory representation, three ordered OreDictionary fuel forms, four output unit forms, the loaded and current configuration, and explicit installed extraction policies. Fuel matching prefers block, then ingot, then nugget. Loaded fuel units have factors 81/9/1; output units have factors 1/9/81/729. Current configuration and initialized constants are kept separately because reloading configuration need not reinitialize final ContainerReactor fields. Native zero configuration values are retained rather than clamped; zero unit values do not imply a usable conversion ratio.

Manual access exists when the reactor is OFFLINE. The container first refunds remaining fuel, choosing blocks only when the equivalent ingot count reaches 64, then ingots/nuggets. After fuel is exhausted it offers large chaos fragments when the equivalent small-fragment count reaches 64, otherwise small/tiny fragments. The manual branch does not output a full shard. The core automation inventory uses only full shards and requires converted fuel strictly greater than the full-shard unit value, not greater-than-or-equal. Configuration separately controls automation availability.

Energy generation and conversion rate depend on actual reactor state, saturation, temperature, conversion and configuration. No fixed duration, fixed energy amount or guaranteed recipe result is invented. The webpage describes configured units and these rules; it does not simulate a player's running reactor or replace native item visuals with recipe GUI captures.

Java local verification runs actual installed remapped ConfigHandler/ContainerReactor class initialization with controlled configuration and registered vanilla item specimens. It confirms the getters/constants, 1296 block units and 11664 full-shard units at the controlled 16/16 base values, and configuration drift. It does not prove installed ModBlocks/ModItems registrations, renderer correctness, complete operational simulation or server synchronization; those remain for live preflight/acceptance. Compiler full-domain validation and the shared frontend query validate the Java record and reject a forged 1:1 conversion, incomplete roles, nonfinite multipliers, consuming classification and missing item closure.
