# Native filter results (source 15 / catalog 14)

Compiler and contracts 0.15.0 consume NESQL 0.16.0 source revision 15.
Catalog revision is 14 (the preceding catalog revision was 13, even though
source revision was 14). Old release bundles and catalogs remain immutable;
use their matching compiler/web bundle. There is no migration reader.

Automagy 0.28.2 `PreserveFilterRecipe` starts with a copy of the recipe output.
The first filter encountered in inventory order supplies configuration. A later
filter supplies metadata; if absent, metadata remains that of the base output.
If there is no filter, the output remains fixed. Item type and count always
come from the base. Alternatives with different inventory roles cannot share
one projection and remain explicitly unsupported pending separate branches.

`Filter.configurations` contains one native `InventoryWithFilterOptions`
serialization for every configuration choice, in matching order. These are
runtime observations: resolving the legacy numeric item ids in `ContainedItems`
requires the game's registry and must not be guessed by the offline compiler.
NESQL observes them on copied stacks. The compiler verifies list shape, slots,
stack field types, allowed root fields and option normalization. It then checks
every output sample against the base plus this observation. This validates the
contract; it does not independently prove which item ids the game registered.

The serializer always replaces `ContainedItems` (including an empty end list),
rebuilds or deletes `FilterOptions`, and retains unrelated base tags. It does
not copy unrelated input tags. Boolean options use Minecraft numeric-to-byte
conversion; name filters use Java trim (characters <= U+0020). A metadata input
must follow the configuration input. With metadata, all configuration choices
must give identical tags or require separate branches. Without metadata,
samples bind to each configuration choice and retain the base metadata.

`filter-native-fixtures.json` was generated by executing Automagy 0.28.2's
native serializer/crafting code in the isolated Java test registry. Original
jar SHA256: `4c1d78e0adee1754675d93ffbadc8c9fe205710cb77538b953e57810f9528efc`.
The test-only derivative renames SRG members to MCP; no mod bytecode is shipped
in the compiler. The NESQL `nativeFilterTest` task reproduces these observations.
This is offline evidence, not real-game export acceptance.
